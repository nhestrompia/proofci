# ProofCI

> Unit tests check examples. ProofCI checks declared correctness properties on every pull request.

ProofCI is a GitHub Action that stops a pull request, whether a person or a
coding agent wrote it, from silently breaking a guarantee you have already
proved about your Rust code. It translates the pull request's Rust into Lean
with [Charon](https://github.com/AeneasVerif/charon) and
[Aeneas](https://github.com/AeneasVerif/aeneas). It then requires a Lean
proof of every guarantee you declared, checked by the Lean kernel.

It runs on GitHub's free hosted runners. There is no service to sign up for and
nothing to host.

```
PR #42 · ProofCI

✅ fees/fee-capped            ledger::calculate_fee   verified
✅ fees/zero-amount           ledger::calculate_fee   verified
❌ transfer/conservation      ledger::transfer        unproven
✅ transfer/rejects-overdraft ledger::transfer        verified
```

## What it checks, and what it doesn't

ProofCI verifies **explicitly declared properties of selected functions** on
every pull request. It does not claim to prove the whole application correct.

| | Supported now | Out of scope |
|---|---|---|
| Language | A safe, self-contained Rust crate (no dependencies, build scripts, proc macros or `unsafe`) | Other languages; crates with dependencies |
| Code | Functions Aeneas can translate: pure functions and deterministic state transitions over integers, structs, enums, `Option`/`Result`, loops, `Vec` and borrows | Threads, I/O, FFI, constructs Aeneas rejects |
| Properties | Any Lean statement: pre/postconditions, invariants, "never panics or overflows", equivalence | Informal claims such as "secure" |
| Evidence | Lean proofs accepted by the Lean kernel **and** nanoda, using only `propext`, `Quot.sound` and `Classical.choice` | Tests, `sorry`, extra axioms, `native_decide` |

A verified result means the exact protected Lean statement holds for the Rust
code *as translated by the pinned Charon/Aeneas toolchain*. The Rust compiler,
Charon and Aeneas are trusted. Integer overflow and panics are modelled as
failures, so a proof that a call succeeds also proves it neither overflows nor
panics.

## How a repository is set up

```
your-repo/
├── Cargo.toml, src/lib.rs     # your Rust crate
├── proofci.yaml               # which guarantees are required
└── proofci/
    ├── Contract.lean          # what they mean (protected: read from the base branch)
    └── Proofs.lean            # why they hold (updated by the PR, e.g. by your agent)
```

**`proofci.yaml`** lists the guarantees. YAML is not a formal language, so it
only *names* Lean theorems and never contains formulas.

```yaml
version: 1
crate: .          # path to the Cargo package (default ".")
lean: proofci     # directory with Contract.lean and Proofs.lean (default "proofci")

targets:
  - id: transfer
    function: ledger::transfer          # Rust path of the function
    guarantees:
      - id: conservation
        theorem: transfer_conserves     # theorem in Contract.lean
      - id: rejects-overdraft
        theorem: transfer_rejects_overdraft
        required: true                  # default; `false` reports without blocking
```

**`proofci/Contract.lean`** states each guarantee about the translated Rust
function. Each statement must mention its target function, so it actually
constrains the implementation. Statements end in `sorry`: they are the
contract, not the proofs.

```lean
import Ledger            -- the Lean translation of your crate (generated by ProofCI)
open Aeneas Aeneas.Std Result ledger

/-- Never panics, and a successful transfer conserves the total balance. -/
theorem transfer_conserves (a : Accounts) (amount : Std.U64) :
    transfer a amount ⦃ r => ∀ b, r = some b → b.from.val + b.to.val = a.from.val + a.to.val ⦄ := by
  sorry
```

`f x ⦃ r => P r ⦄` means "the call succeeds and its result satisfies `P`".

**`proofci/Proofs.lean`** restates each theorem with exactly the same statement
and proves it. Helper modules can live under `proofci/Proofs/`. Proofs may
import `Aeneas` and anything it imports, which includes much of Mathlib.

See [`examples/ledger`](examples/ledger) for a complete, verified example.

## Add it to a repository

Create `.github/workflows/proofci.yml` on your default branch:

```yaml
name: ProofCI
on:
  pull_request_target:          # the workflow and policy come from the base branch
    types: [opened, synchronize, reopened]
  merge_group:
  push:
    branches: [main]
permissions:
  contents: read
  pull-requests: read           # only to read approvals of policy changes
jobs:
  proofci:
    runs-on: ubuntu-latest      # any Linux runner, x86_64 or arm64
    timeout-minutes: 30
    steps:
      - uses: nhestrompia/proofci@COMMIT_SHA   # pin a release commit
        with:
          path: .                              # directory containing proofci.yaml
```

Then make `ProofCI / proofci` a required status check in your branch
protection or ruleset.

Why `pull_request_target`? Under plain `pull_request`, the pull request can
edit the workflow that judges it. Under `pull_request_target`, GitHub runs the
workflow from the base branch. The action checks the pull request out as data
only:

- with a read-only token
- with no persisted credentials and no secrets
- running every tool on it inside an offline container, nested in
  bubblewrap sandboxes

## A pull request cannot weaken its own guarantees

ProofCI reads `proofci.yaml` and `Contract.lean` from the **base** commit; the
pull request contributes only Rust code and proofs. Any Lean translation
committed in the repository is ignored, because ProofCI regenerates it from
the pull request's Rust.

If a pull request removes a guarantee, makes it optional or edits the
contract, the check is blocked and lists the change. It can pass only after
two things happen:

1. A repository owner, member or collaborator who is not the author
   **approves the pull request on that exact commit**.
2. Someone re-runs the job.

A later push needs a new approval.

## Results

| Status | Meaning | Blocks |
|---|---|---|
| `verified` | The kernel accepted a proof of the exact protected statement | no |
| `unproven` | The proof is missing, uses `sorry`, proves a different statement, or no longer checks | if required |
| `contract-stale` | The protected statement no longer type-checks against the new code (for example, a signature changed); a maintainer must update the contract | if required |
| `unsupported` | Charon or Aeneas cannot translate the code, or the function depends on untranslated code | if required |

When a single proof breaks, the other guarantees are still judged. ProofCI
removes the failing declarations and judges what remains. Removing proofs can
only reject more, never accept more. The job summary shows the Lean error.

## Run it locally

```sh
docker run --rm --network none \
  --security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined \
  -v "$PWD:/base:ro" -v "$PWD:/head:ro" \
  ghcr.io/nhestrompia/proofci-toolchain:TAG check --base /base --head /head
```

To compare a branch against its base, use two checkouts (`git worktree add`).
The relaxed security options let bubblewrap create its own sandboxes inside
the container.

## Toolchain

[`toolchain/Dockerfile`](toolchain/Dockerfile) pins every component by version
and SHA-256:

- Lean 4.35.0
- Mathlib v4.35.0
- Aeneas nightly-2026.11.02
- Charon at the commit Aeneas pins
- Rust nightly-2026-09-17

Mathlib is pruned to the modules Aeneas imports. The image is 1.7 GB
compressed and built for Linux x86_64 and arm64; Docker picks the right one.
CI publishes it to GHCR from `main`.

Measured on a free `ubuntu-24.04-arm` GitHub runner, the example takes 26 s
to check once the image is available: translation 1.6 s, contract 8.1 s,
proofs 16.1 s. On a 10-core arm64 machine it takes 13 s. Building the image
from scratch takes about 17 minutes, which is why CI publishes it once and
users pull it.

## Development

```sh
docker buildx build -f toolchain/Dockerfile -t proofci-toolchain:dev --load .
docker run --rm --network none \
  --security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined \
  -v "$PWD:/src:ro" -w /src -e PYTHONPATH=/src \
  --entrypoint python3 proofci-toolchain:dev -m tests.run_scenarios --jobs 4
```

The image is built in two parts. The **toolchain base** (`--target toolchain`)
holds Rust, Charon, Lean, Mathlib and Aeneas and changes only when a pin in
`toolchain/` changes. `main` publishes it under a hash of `toolchain/`.
[`toolchain/Release.Dockerfile`](toolchain/Release.Dockerfile) adds ProofCI's
code on top in seconds. Pull requests that leave `toolchain/` alone pull the
published base and run the scenarios as 5 parallel shards per architecture.
Pull requests that change a pin rebuild the base, which takes about 20 minutes.

[`tests/test_scenarios.py`](tests/test_scenarios.py) runs the real toolchain
against 20 adversarial changes to the example and checks every resulting
status:

- **Wrong code:** a buggy fee, an overflowing transfer, a renamed function, a
  changed signature, a call into standard-library code Aeneas does not model
- **Fake proofs:** `sorry`, a weakened statement, a fake model of the code, a
  committed fake translation, an extra `axiom`, `native_decide`, a theorem
  added with kernel checking switched off, citing the contract's own `sorry`
- **Attacks on the checker:** proof code that writes to the contract and model
  sources, or recompiles a weaker contract into the build directory while it
  builds (both rejected: proof code only ever runs in a disposable copy of
  the workspace)
- **Policy and scope:** a weakened policy, `unsafe` code, a new dependency, a
  broken import
